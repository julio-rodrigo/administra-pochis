# Pochis Module

## 1. Purpose

The Pochis module manages the moto-taxis registered in AdministraPochi.

In the application's domain, a **pochi** is a moto-taxi. Although this concept could be described generically as a vehicle, the project must consistently use the domain term `Pochi` in Java classes, DTOs, services, endpoints, tests, and documentation.

This document contains the module-specific requirements. All implementation, architecture, validation, exception handling, mapping, and testing conventions defined in `.github/copilot-instructions-backend.md` also apply.

The existing Users module must be used as the reference implementation for package structure, naming conventions, dependency injection, DTO organization, MapStruct configuration, exception handling, and unit test style.

## 2. Naming Convention

Use the following names consistently:

- Domain name: `Pochi`
- Plural domain name: `Pochis`
- Database table: `pochis`
- Base REST path: `/api/pochis`
- Entity: `Pochi`
- Repository: `PochiRepository`
- Mapper: `PochiMapper`
- Service: `PochiService`
- Controller: `PochiController`
- Create request: `CreatePochiRequest`
- Update request: `UpdatePochiRequest`
- Response DTO: `PochiResponse`

Do not use `Vehicle`, `Vehicles`, `vehicle`, or `/api/vehicles` in the implementation of this module.

## 3. Existing Database Schema

The module is based on the following PostgreSQL table, which already exists:

```sql
CREATE TABLE pochis (
    id INTEGER GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    economic_number VARCHAR(10) NOT NULL,
    license_plate VARCHAR(10),
    union_name VARCHAR(15) NOT NULL DEFAULT 'UNTRAC',
    owner_id INTEGER NOT NULL REFERENCES users(id),
    active BOOLEAN NOT NULL DEFAULT TRUE,
    created_at TIMESTAMP WITH TIME ZONE NOT NULL DEFAULT CURRENT_TIMESTAMP,
    updated_at TIMESTAMP WITH TIME ZONE NOT NULL DEFAULT CURRENT_TIMESTAMP,

    CONSTRAINT uk_pochis_economic_number UNIQUE (economic_number),
    CONSTRAINT uk_pochis_license_plate UNIQUE (license_plate)
);
```

The application must map to this schema as it currently exists. Do not create or modify the table from application code as part of this module.

## 4. Entity Mapping

Create a `Pochi` JPA entity mapped to the `pochis` table.

| Database column | Java field | Java type | Rules |
|---|---|---|---|
| `id` | `id` | `Integer` | Primary key, identity generated |
| `economic_number` | `economicNumber` | `String` | Required, maximum 10 characters, unique |
| `license_plate` | `licensePlate` | `String` | Optional, maximum 10 characters, unique when provided |
| `union_name` | `unionName` | `String` | Required, maximum 15 characters, defaults to `UNTRAC` |
| `owner_id` | `owner` | `User` | Required foreign key to `users.id`; lazy many-to-one |
| `active` | `active` | `Boolean` | Required, defaults to `true` |
| `created_at` | `createdAt` | Project-standard timezone-aware type | Generated by the application/database and not supplied by clients |
| `updated_at` | `updatedAt` | Project-standard timezone-aware type | Updated whenever the record changes and not supplied by clients |

Use the same timestamp strategy already established by the Users module. Do not introduce a different auditing approach only for Pochis.

Do not use Lombok unless it is already part of the project and used consistently by the Users module.

## 5. Relationships

Every Pochi has exactly one owner, represented by a required relationship to `User`:

```java
@ManyToOne(fetch = FetchType.LAZY, optional = false)
@JoinColumn(name = "owner_id", nullable = false)
private User owner;
```

One user can own multiple Pochis. Both `OWNER` and `ADMIN` users can own Pochis:
roles represent access levels, while ownership is determined exclusively by
`pochis.owner_id`. Do not infer ownership from the user's role or create an
Owners entity/table. No reverse collection or cascading user operations are required.

The service resolves `ownerId` with `UserRepository.findById` and assigns the
resulting entity. MapStruct must not perform database lookups or construct owner
entities from request identifiers. No role-based authorization or active-user
restriction is introduced here.

Do not add `createdBy`, `updatedBy`, or driver assignment relationships.

Future modules may reference `pochis.id`, but those relationships belong to the specifications of those modules.

## 6. DTOs

### 6.1 CreatePochiRequest

Fields:

- `economicNumber`
- `licensePlate`
- `unionName`
- `ownerId`

Rules:

- `economicNumber` is required, must not be blank, and must contain at most 10 characters.
- `licensePlate` is optional. When provided, it must not be blank after normalization and must contain at most 10 characters.
- `unionName` is optional in the creation request. When omitted or blank, the service must use `UNTRAC`. When provided, it must contain at most 15 characters.
- `ownerId` is required (`@NotNull`) and must identify an existing user with either supported role.
- The client must not provide `id`, `active`, `createdAt`, or `updatedAt`.
- A newly created Pochi must always start as active.

### 6.2 UpdatePochiRequest

Fields:

- `economicNumber`
- `licensePlate`
- `ownerId`

Rules:

- `economicNumber` is required, must not be blank, and must contain at most 10 characters.
- `licensePlate` is optional and must contain at most 10 characters when provided.
- `ownerId` is required (`@NotNull`). The service resolves the user and replaces the owner relationship, allowing ownership transfers.
- The request must not modify `id`, `active`, `unionName`, `createdAt`, or `updatedAt`.
- Status changes must use the dedicated activation and deactivation operations.

### 6.3 PochiResponse

Return:

- `id`
- `economicNumber`
- `licensePlate`
- `unionName`
- `ownerId`
- `active`
- `createdAt`
- `updatedAt`

Never return the JPA entity directly from a controller.
`ownerId` identifies the owner without exposing a complete User, password hash,
or other user details. It is returned on create, update, lookup, list, and status responses.

## 7. Normalization Rules

Before validating uniqueness or persisting data:

- Trim leading and trailing whitespace from `economicNumber`, `licensePlate`, and `unionName`.
- Store `economicNumber`, `licensePlate`, and `unionName` in uppercase for consistent comparison and presentation.
- Convert a null or blank `licensePlate` to `null`.
- On creation, convert a null or blank `unionName` to `UNTRAC`.

Uniqueness checks must use the normalized values. For example, `p-01`, ` P-01 `, and `P-01` must be treated as the same economic number.

## 8. Business Rules

1. Every Pochi must have an economic number.
2. The economic number must be unique.
3. A license plate is optional.
4. When a license plate is provided, it must be unique.
5. Multiple rows may have a null license plate, according to PostgreSQL unique constraint behavior.
6. The default union name is `UNTRAC`.
7. Every newly created Pochi must be active.
8. Pochis must not be physically deleted through this module.
9. Deactivation must set `active` to `false`.
10. Activation must set `active` to `true`.
11. Updating a Pochi must not report a duplicate when the unique value belongs to the same record being updated.
12. `createdAt` must remain unchanged after creation.
13. `updatedAt` must reflect the most recent successful modification, activation, or deactivation.
14. Every Pochi must reference exactly one existing user through `owner_id`.
15. A user can own multiple Pochis regardless of whether their role is `OWNER` or `ADMIN`.
16. Changing a user's role does not change ownership; only updating `ownerId` transfers ownership.

## 9. Repository Requirements

Create `PochiRepository` using Spring Data JPA.

It must support the operations required to:

- Find a Pochi by identifier.
- List Pochis.
- Check whether an economic number already exists.
- Check whether a license plate already exists when a license plate is provided.
- Check duplicates during update while excluding the current Pochi identifier.

Use derived query names that follow the existing project conventions. Do not add custom JPQL or native SQL unless it is necessary.

## 10. Service Operations

The service must provide operations equivalent to:

- Create a Pochi.
- Get a Pochi by ID.
- List all Pochis.
- Update a Pochi.
- Activate a Pochi.
- Deactivate a Pochi.

The exact method signatures must follow the conventions established by the Users module.

### Creation

- Normalize the input.
- Validate economic number uniqueness.
- Validate license plate uniqueness when provided.
- Resolve the required `ownerId` using `UserRepository`; fail with `UserNotFoundException` if the user does not exist.
- Apply `UNTRAC` when `unionName` is omitted or blank.
- Set `active` to `true`.
- Set timestamps according to the existing project strategy.
- Map and return `PochiResponse`.

### Update

- Fail when the Pochi does not exist.
- Normalize the input.
- Validate economic number uniqueness excluding the current record.
- Validate license plate uniqueness excluding the current record when provided.
- Resolve the required `ownerId` using `UserRepository` before modifying the Pochi and assign the resolved user.
- Preserve `id`, `active`, and `createdAt`.
- Update `updatedAt` according to the existing project strategy.
- Map and return `PochiResponse`.

### Activation and deactivation

- Fail when the Pochi does not exist.
- Update only the `active` state and `updatedAt`.
- The operations must be idempotent: activating an active Pochi or deactivating an inactive Pochi must not produce an error.
- Return the updated `PochiResponse`, following the Users module convention.

## 11. REST API

Implement the endpoints using the same response and controller conventions as the Users module.

| Method | Path | Purpose | Expected successful status |
|---|---|---|---|
| `POST` | `/api/pochis` | Create a Pochi | `201 Created` |
| `GET` | `/api/pochis` | List Pochis | `200 OK` |
| `GET` | `/api/pochis/{id}` | Get a Pochi by ID | `200 OK` |
| `PUT` | `/api/pochis/{id}` | Update a Pochi | `200 OK` |
| `PATCH` | `/api/pochis/{id}/activate` | Activate a Pochi | `200 OK` |
| `PATCH` | `/api/pochis/{id}/deactivate` | Deactivate a Pochi | `200 OK` |

Do not implement a physical `DELETE /api/pochis/{id}` endpoint.

If the Users module already uses a different but equivalent status endpoint convention, preserve project consistency and document the chosen route in the implementation.

## 12. Error Scenarios

Use the centralized exception handling defined by the project.

Handle at least:

- Pochi not found: `404 Not Found`.
- Owner user not found: `404 Not Found` using the existing `UserNotFoundException` handler.
- Missing or null `ownerId` on create/update: `400 Bad Request` with a field-level validation error.
- Duplicate economic number: `409 Conflict`.
- Duplicate license plate: `409 Conflict`.
- Invalid request data: `400 Bad Request`.
- Field length violations: `400 Bad Request`.
- Blank required values: `400 Bad Request`.

Error messages must be clear and must not expose SQL, database constraint names, stack traces, or implementation details.

Suggested messages:

- `Pochi not found with id: {id}`
- `A pochi with economic number '{economicNumber}' already exists`
- `A pochi with license plate '{licensePlate}' already exists`

Reuse existing project exceptions when their meaning matches these scenarios.

## 13. MapStruct Requirements

Create `PochiMapper` following the Users module MapStruct configuration.

The mapper must:

- Convert `Pochi` to `PochiResponse`.
- Map `owner.id` to `PochiResponse.ownerId`.
- Convert `CreatePochiRequest` to `Pochi` while ignoring generated and system-controlled fields.
- Ignore `owner` when mapping create/update requests; the service resolves and assigns it.
- Apply updates without replacing `id`, `active`, `createdAt`, or `updatedAt` from client input.
- Avoid manual field-by-field mapping when MapStruct can perform the conversion.

Normalization and business defaults belong in the service or an established project normalization mechanism, not in the controller.

## 14. Unit Testing Requirements

Create unit tests following the structure and naming conventions of the Users module.

At minimum, service unit tests must cover:

### Creation

- Creates a Pochi successfully.
- Uses `UNTRAC` when `unionName` is omitted or blank.
- Sets a newly created Pochi as active.
- Accepts a null license plate.
- Normalizes text fields.
- Rejects a duplicate economic number.
- Rejects a duplicate license plate.
- Does not check license plate duplication when the normalized plate is null.
- Creates a Pochi with an `OWNER` user.
- Creates a Pochi with an `ADMIN` user as owner.
- Rejects requests without `ownerId` before invoking the service.
- Rejects nonexistent owner IDs without persisting.

### Retrieval

- Returns a Pochi by ID.
- Throws the expected not-found exception for an unknown ID.
- Lists Pochis successfully.
- Handles an empty list according to the Users module convention.
- Returns `ownerId` without exposing the complete User entity.

### Update

- Updates a Pochi successfully.
- Preserves `id`, `active`, and `createdAt`.
- Allows the record to retain its current economic number.
- Allows the record to retain its current license plate.
- Rejects an economic number used by a different Pochi.
- Rejects a license plate used by a different Pochi.
- Allows removal of an optional license plate by setting it to null or blank.
- Throws the expected not-found exception for an unknown ID.
- Changes the owner using an existing user's ID.
- Rejects a nonexistent new owner without changing the existing relationship.

### Status

- Deactivates an active Pochi.
- Deactivating an already inactive Pochi is idempotent.
- Activates an inactive Pochi.
- Activating an already active Pochi is idempotent.
- Activation and deactivation fail for an unknown ID.

Use JUnit 5, Mockito, and AssertJ. Mock the repository and mapper in service unit tests. Verify meaningful outcomes and dependency interactions without over-specifying implementation details.

Add controller tests when needed to verify request validation, HTTP status codes, serialization, and centralized exception translation, following the strategy already used in the project.

Run the complete test suite and verify the JaCoCo rules configured in `backend/pom.xml`. Do not reduce coverage thresholds or add unjustified exclusions.

## 15. Out of Scope

The following are not part of this module:

- Driver assignments to a Pochi.
- Spring Security or authorization rules.
- An Owners entity/table, multiple roles per user, or role tables.
- Payment or fee records.
- Expense records.
- Financial auditing.
- `createdBy` or `updatedBy` relationships.
- Physical deletion.
- Pagination, filtering, or sorting unless already required by the Users module convention.
- Database migrations or constraint renaming.

## 16. Definition of Done

The Pochis module is complete when:

- All classes and endpoints use the domain term `Pochi` rather than `Vehicle`.
- The entity maps correctly to the existing `pochis` table.
- DTOs, mapper, repository, service, controller, validations, and exceptions follow `.github/copilot-instructions-backend.md`.
- The implementation follows the existing Users module pattern.
- No unsupported relationships or audit fields are introduced.
- Required ownership is resolved by the service and exposed safely as `ownerId`.
- Duplicate economic numbers and license plates are handled correctly.
- Activation and deactivation replace physical deletion.
- Unit tests cover successful and failure scenarios.
- The complete test suite passes.
- The JaCoCo verification configured in `backend/pom.xml` passes.
