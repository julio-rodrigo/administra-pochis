# Administration Fee Rules Module

## 1. Purpose

The Administration Fee Rules module defines how much administration fee must be charged for a Pochi according to:

- The Pochi that worked.
- The work date.
- The number of worked shifts.
- The applicable rule validity period.
- Whether a Pochi-specific rule exists.

Administration fees are not general expenses.

An administration fee is compensation for the administrative work involved in recovering and registering the settlements generated by a Pochi.

This module only manages administration fee rules.

The generation and persistence of actual administration charges will be implemented later in the Administration Charges module.

## 3. Business context

A Pochi may work one or two shifts per day.

The supported shifts are the same shifts already used by the Pochi Assignments module:

```text
MORNING
AFTERNOON
```

The number of worked shifts is interpreted as follows:

| Assignments for the date | Worked shifts |
|---|---:|
| No assignment | 0 |
| MORNING only | 1 |
| AFTERNOON only | 1 |
| MORNING and AFTERNOON | 2 |

Administration fees are not calculated as a fixed amount multiplied by the number of shifts.

For example, the global rule may be:

```text
1 worked shift  = $50.00
2 worked shifts = $70.00
```

Therefore:

```text
$50.00 × 2 shifts = $100.00
```

is incorrect.

The correct administration fee for two shifts is the explicitly configured `twoShiftAmount`:

```text
2 worked shifts = $70.00
```

---

## 4. Global rule and Pochi-specific rules

The module supports two rule scopes.

### 4.1 Global rule

A global rule applies to every Pochi that does not have a specific rule for the requested date.

A global rule is represented by:

```text
pochiId = null
```

Example:

```text
Global rule

1 shift  = $50.00
2 shifts = $70.00
```

### 4.2 Pochi-specific rule

A Pochi-specific rule overrides the global rule for a particular Pochi during its validity period.

A specific rule is represented by:

```text
pochiId != null
```

Example:

```text
Pochi 16 rule

1 shift  = $60.00
2 shifts = $80.00
```

Given the previous examples:

```text
Pochi 15 with one shift
No specific rule exists
Result: global rule = $50.00
```

```text
Pochi 16 with one shift
A specific rule exists
Result: Pochi-specific rule = $60.00
```

The application must always search for a Pochi-specific rule first.

If no Pochi-specific rule exists for the requested date, it must use the applicable global rule.

---

## 5. Rule validity

Administration fee rules are effective-dated.

Each rule contains:

```text
validFrom
validTo
```

`validFrom` is inclusive.

`validTo` is also inclusive when present.

A `null` `validTo` means that the rule has no defined end date.

A rule is applicable for a date when:

```text
validFrom <= requestedDate
```

and:

```text
validTo is null
OR
validTo >= requestedDate
```

Example:

```text
validFrom = 2026-01-01
validTo   = 2026-12-31
```

The rule applies from January 1, 2026 through December 31, 2026, including both dates.

---

## 6. Historical integrity

Administration fee amounts may change over time.

Existing historical rules must not be overwritten when a fee changes.

Example:

```text
Old global rule

validFrom       = 2026-01-01
validTo         = 2026-12-31
oneShiftAmount  = $50.00
twoShiftsAmount = $70.00
```

```text
New global rule

validFrom       = 2027-01-01
validTo         = null
oneShiftAmount  = $60.00
twoShiftsAmount = $80.00
```

The new rule must not modify the amounts of the old rule.

When a price changes:

1. Close the current rule by setting its `validTo`.
2. Create a new rule with the new amounts and a new `validFrom`.
3. Preserve the old rule for historical queries.

## 7. Relationship with Pochi Assignments and Settlements

This module only defines administration fee amounts.

It does not generate administration charges.

The future Administration Charges module will use information from:

```text
Pochi Assignments
Settlements
Administration Fee Rules
```

A Pochi Assignment proves that the Pochi worked a shift.

A completed Settlement proves that the corresponding liquidation was recovered and registered by the administrator.

The future charge generation rule will require both conditions.

```text
Pochi Assignment exists
AND
the corresponding Settlement has been registered
```

### One worked shift

If the Pochi worked only one shift, the administration charge may become eligible when that shift has a valid Settlement.

```text
MORNING assignment     = yes
MORNING settlement     = yes
AFTERNOON assignment   = no

Eligible result:
1 shift administration amount
```

The same applies when only the AFTERNOON shift was worked.

### Two worked shifts

If the Pochi worked both shifts, the administration charge must not become eligible until the Settlements covering both shifts have been registered.

Example:

```text
MORNING assignment     = yes
MORNING settlement     = yes

AFTERNOON assignment   = yes
AFTERNOON settlement   = no
```

Result:

```text
Administration charge is not eligible yet.
```

Once the AFTERNOON Settlement is registered:

```text
MORNING assignment     = yes
MORNING settlement     = yes

AFTERNOON assignment   = yes
AFTERNOON settlement   = yes
```

Result:

```text
Administration charge becomes eligible using twoShiftAmount.
```

The future Administration Charge will belong to:

```text
Pochi + work date
```

It will not create an independent full administration fee for each Settlement.

For example, given:

```text
oneShiftAmount  = $50.00
twoShiftsAmount = $70.00
```

two Settlements must produce one daily administration charge of:

```text
$70.00
```

They must not produce:

```text
$50.00 + $50.00 = $100.00
```

### Partial Settlement amount

A Settlement may be accepted even when the received amount is lower than the expected amount.

Example:

```text
Expected amount = $400.00
Received amount = $300.00
```

If the Settlement was validly registered and the remaining amount was handled through the Driver Debts module, the administrative work is considered performed.

Administration charge eligibility must not require:

```text
expectedAmount == receivedAmount
```

That decision belongs to the future Administration Charges module and must not be implemented inside Administration Fee Rules.

## 8. Database structure

The existing table is:

```sql
CREATE TABLE administration_fee_rules (
    id INTEGER GENERATED ALWAYS AS IDENTITY PRIMARY KEY,

    pochi_id INTEGER NULL,

    one_shift_amount NUMERIC(10, 2) NOT NULL,
    two_shifts_amount NUMERIC(10, 2) NOT NULL,

    valid_from DATE NOT NULL,
    valid_to DATE NULL,

    active BOOLEAN NOT NULL DEFAULT TRUE,

    created_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP,
    updated_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP,

    CONSTRAINT fk_administration_fee_rules_pochi
        FOREIGN KEY (pochi_id)
        REFERENCES pochis(id),

    CONSTRAINT chk_administration_fee_rules_one_shift_amount
        CHECK (one_shift_amount >= 0),

    CONSTRAINT chk_administration_fee_rules_two_shifts_amount
        CHECK (two_shifts_amount >= 0),

    CONSTRAINT chk_administration_fee_rules_valid_dates
        CHECK (valid_to IS NULL OR valid_to >= valid_from)
);
```

Indexes:

```sql
CREATE INDEX idx_administration_fee_rules_pochi_id
    ON administration_fee_rules(pochi_id);

CREATE INDEX idx_administration_fee_rules_validity
    ON administration_fee_rules(valid_from, valid_to);

CREATE INDEX idx_administration_fee_rules_pochi_validity
    ON administration_fee_rules(pochi_id, valid_from, valid_to);
```

The initial global rule is:

```sql
INSERT INTO administration_fee_rules (
    pochi_id,
    one_shift_amount,
    two_shifts_amount,
    valid_from
)
VALUES (
    NULL,
    50.00,
    70.00,
    '2026-11-13'

```

## 14. Applicable rule resolution

The most important service operation is:

```java
findApplicableRule(pochiId, date)
```

The resolution order must be:

1. Validate that the Pochi exists.
2. Search for an active Pochi-specific rule applicable on the requested date.
3. If found, return that rule.
4. Otherwise, search for an active global rule applicable on the requested date.
5. If found, return the global rule.
6. If neither exists, throw the appropriate business exception.

Conceptual pseudocode:

```java
public AdministrationFeeRuleResponse findApplicableRule(
        Integer pochiId,
        LocalDate date
) {
    validatePochiExists(pochiId);

    return repository
        .findApplicablePochiRule(pochiId, date)
        .or(() -> repository.findApplicableGlobalRule(date))
        .map(mapper::toResponse)
        .orElseThrow(() -> new BusinessException(
            "No applicable administration fee rule was found"
        ));
}
```

The exact implementation must follow the exception and repository conventions already used in the project.

## 15. Overlapping validity periods

The application must reject overlapping rules for the same scope.

### Invalid global overlap

Existing rule:

```text
pochiId  = null
validFrom = 2026-01-01
validTo   = 2026-12-31
```

New rule:

```text
pochiId  = null
validFrom = 2026-06-01
validTo   = null
```

This must be rejected because both global rules apply during part of the same period.

### Invalid Pochi overlap

Existing rule:

```text
pochiId   = 16
validFrom = 2026-01-01
validTo   = 2026-12-31
```

New rule:

```text
pochiId   = 16
validFrom = 2026-11-01
validTo   = null
```

This must also be rejected.

### Allowed overlap between different scopes

The following is valid:

```text
Global rule
validFrom = 2026-01-01
validTo   = null
```

```text
Pochi 16 rule
validFrom = 2026-06-01
validTo   = null
```

They may overlap because the Pochi-specific rule intentionally overrides the global rule for Pochi 16.

### Allowed overlap between different Pochis

Rules belonging to different Pochis may use the same validity period.

```text
Pochi 15 rule: 2026-01-01 to null
Pochi 16 rule: 2026-01-01 to null
```

This is valid.

### Overlap formula

Two inclusive date ranges overlap when:

```text
newValidFrom <= existingValidTo
AND
existingValidFrom <= newValidTo
```

A null end date must be treated as an open-ended future date for overlap validation.

This validation belongs in the service layer.

## 16. Additional business validations

The service must enforce the following rules.

### Amount validation

```text
oneShiftAmount >= 0
twoShiftsAmount >= 0
```

Additionally:

```text
twoShiftsAmount >= oneShiftAmount
```

This prevents a two-shift fee from being lower than a one-shift fee.

The database currently guarantees non-negative amounts. The relation between both amounts must at least be enforced by the service.

### Date validation

```text
validTo is null
OR
validTo >= validFrom
```

### Pochi validation

When `pochiId` is provided:

- The Pochi must exist.
- The service must load the existing Pochi.
- A nonexistent Pochi must produce the project-standard not-found exception.

When `pochiId` is null:

- The rule is global.
- No Pochi lookup is required.

### Duplicate applicable rules

The service must never silently select one rule when multiple active rules are applicable to the same scope and date.

Overlapping rules must be prevented during create and update operations.

### Validity and active state

A rule is applicable only when both are true:

```text
active = true
```

and:

```text
requested date is within validFrom and validTo
```

## 17. Update behavior

Updates must preserve historical integrity.

A normal update may be used to:

- Correct a recently created rule that has not been used.
- Close an open validity period by setting `validTo`.
- Activate or deactivate a rule.
- Correct data when business rules allow it.

A normal update must not be used to overwrite historical amounts after those amounts have been used by administration charges.

The Administration Charges module will later determine whether a rule has already been referenced.

Until that module exists, document and implement the intended behavior carefully without creating fake dependencies on a table that does not exist yet.

Do not implement Administration Charges as part of this module.

---

## 18. Deactivation and deletion

Prefer logical deactivation over physical deletion.

Deactivation should set:

```text
active = false
```

Physical deletion should not be exposed as a standard operation because rules are historical financial configuration.

Once Administration Charges reference these rules, deleting them could destroy financial traceability.

If the existing application architecture requires a delete endpoint for consistency, it must only be allowed for rules that have never been used. However, the preferred initial implementation is not to provide physical deletion.

## 26. Acceptance criteria

The module is complete when:

1. A global administration fee rule can be created.
2. A Pochi-specific administration fee rule can be created.
3. Rules preserve `validFrom` and `validTo`.
4. Overlapping global rules are rejected.
5. Overlapping rules for the same Pochi are rejected.
6. A specific rule overrides the global rule.
7. The global rule is used when no specific rule applies.
