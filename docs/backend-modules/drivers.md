# Drivers Module

## Objective

Implement the Drivers module following the existing architecture, conventions, coding style, validation strategy, exception handling, mapping strategy, and testing patterns already established in the Users and Pochis modules.

Do not introduce a different architectural pattern.

The module must follow the existing layered structure:

Controller
↓
Service
↓
Repository
↓
Database

DTOs
↕
MapStruct Mapper
↕
Entities

The Drivers module consists of three related resources:

- Driver
- Driver License
- Driver Absence

A Driver is the main aggregate and represents a person who can operate a pochi.

Driver-to-pochi and shift assignments DO NOT belong to this module.
They will be implemented later in the Pochis Assignments module.

- `updated_at` TIMESTAMP
- `deleted` BOOLEAN, default FALSE
- `deleted_at` TIMESTAMP, nullable

The database enum `driver_status` contains:

- ACTIVE
- INACTIVE

The database enum `blood_type` contains:

- A_POSITIVE
- A_NEGATIVE
- B_POSITIVE
- B_NEGATIVE
- AB_POSITIVE
- AB_NEGATIVE
- O_POSITIVE
- O_NEGATIVE

## Driver License

Table:

`driver_licenses`

Fields:

- `id` INTEGER, primary key, generated by the database
- `driver_id` INTEGER, foreign key to drivers
- `license_type` VARCHAR(20), required, default C4
- `license_number` VARCHAR(50), required and unique
- `issued_at` DATE, required
- `expires_at` DATE, required
- `issuing_municipality` VARCHAR(40), required
- `current_license` BOOLEAN, required, default TRUE
- `created_at` TIMESTAMP
- `updated_at` TIMESTAMP

Relationship:

Driver 1:N DriverLicense

A driver may have multiple licenses historically, but only one license may be marked as current.

The database already enforces this restriction using a partial unique index.

---

## Driver Absence

Table:

`driver_absences`

Fields:

- `id` INTEGER, primary key, generated by the database
- `driver_id` INTEGER, foreign key to drivers
- `start_date` DATE, required
- `end_date` DATE, required
- `reason` VARCHAR(100), optional
- `notes` VARCHAR(500), optional
- `created_at` TIMESTAMP
- `updated_at` TIMESTAMP

Relationship:

Driver 1:N DriverAbsence

An absence may represent either:

- one day
- multiple consecutive days

A one-day absence is represented by:

startDate == endDate

# Important Domain Rules

## Driver lifecycle

Drivers use logical deletion.

A driver must never be physically deleted from the database through the application.

Logical deletion means:

deleted = true
deletedAt = current timestamp

A deleted driver must not appear in normal driver queries.

Do not confuse logical deletion with employment status.

### ACTIVE

The driver currently works for the business.

### INACTIVE

The driver is still a valid historical record but does not currently work for the business.

### deleted = true

The driver record has been logically removed from normal application usage.

A previously inactive driver may become ACTIVE again.

A deleted driver should not be treated as an active application record.

---

# Driver Personal Data

Store the driver's name as separate fields:

- firstName
- firstLastName
- secondLastName

Do not persist a duplicated `fullName` field.

If a full name is required in a response, it should be constructed from the individual name fields.

The second last name is optional.

Avoid generating double spaces or the literal value `null` when constructing a full name.

---

# CURP Rules

CURP:

- is required
- must contain exactly 18 characters
- must be unique
- should be normalized to uppercase
- leading/trailing whitespace should be removed

Do not allow another active or inactive Driver record to be created using an existing CURP.

Logical deletion does not make the CURP reusable.

If a previously registered driver returns to work, the existing driver record should be reactivated instead of creating a duplicate driver.

# Employment Status

Represent employment status using a Java enum.

Suggested enum:

DriverStatus

Values:

- ACTIVE
- INACTIVE

Do not use employment status to represent temporary absences.

A driver can be:

employmentStatus = ACTIVE

while simultaneously having an absence covering the current date.

Absences and employment status represent different concepts.

# Driver License Rules

Licenses must preserve historical information.

Do not overwrite an old license when a driver renews their license.

Instead:

1. Mark the previous license:
   currentLicense = false

2. Create the new license:
   currentLicense = true

Only one license may be current for a driver.

The application should validate this rule even though the database also enforces it.

To manually mark a license as no longer current, provide its ID and send
`currentLicense: false`. This operation must not affect other licenses or
automatically promote a historical license to current.

License numbers are unique.

The license type currently used by the business is:

C4

However, keep `licenseType` as a persisted field to allow future license types without database redesign.

The default license type is C4.

License dates must satisfy:

expiresAt > issuedAt

Do not store license validity as a separate number of years.

Validity is determined using:

issuedAt
expiresAt

License validity status should be calculated instead of persisted.

For example, the application may determine whether a license is:

- valid
- expired

based on `expiresAt`.

Do not create another persisted field for this status.

---

# Driver Absence Rules

Absences represent temporary periods during which an ACTIVE driver is unavailable.

Do not change:

employmentStatus = INACTIVE

when registering a temporary absence.

The absence date range determines whether the driver is currently absent.

The following rule must always be valid:

endDate >= startDate

Example of a single-day absence:

startDate = 2026-11-10
endDate   = 2026-11-10

Example of a multi-day absence:

startDate = 2026-11-10
endDate   = 2026-11-14

Absences do not require an ACTIVE/INACTIVE status.

Do not add soft-delete fields to DriverAbsence.

An absence can be edited by its ID to change `startDate`, `endDate`, `reason`, and
`notes`. The update must preserve the date-range rule and must not change its
associated driver.

# Logical Delete

Deleting a Driver through the application must perform a logical deletion.

Do not call repository.delete() or generate a physical SQL DELETE.

On logical deletion:

deleted = true
deletedAt = current timestamp
employmentStatus = INACTIVE

Normal queries must ignore logically deleted Drivers.

Historical relationships should remain in the database.

Provide a dedicated endpoint to list logically deleted Drivers. Restoring a Driver
must set `deleted = false` and clear `deletedAt`; it must not change the driver's
employment status. A restored Driver remains `INACTIVE` until explicitly changed
through the employment-status operation. Restoring an ID that does not currently
identify a deleted Driver returns the standard not-found response.

Endpoints:

- `GET /api/drivers/deleted`: list logically deleted drivers.
- `PATCH /api/drivers/{id}/restore`: restore one logically deleted driver.
- `PATCH /api/drivers/{id}/activate`: set `employmentStatus` to `ACTIVE`.
- `PATCH /api/drivers/{id}/deactivate`: set `employmentStatus` to `INACTIVE`.
- `PATCH /api/drivers/{driverId}/licenses/{licenseId}/current`: set the license's
  `currentLicense` to `false` using a request body such as
  `{"currentLicense": false}`.
- `PUT /api/drivers/{driverId}/absences/{absenceId}`: update an absence's
  `startDate`, `endDate`, `reason`, and `notes`.
