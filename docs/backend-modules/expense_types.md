# Expense Types Module

## 1. Purpose

The Expense Types module manages the catalog of expense classifications available in AdministraPochi.

An Expense Type defines what kind of expense may be registered in the system.

Examples:

- Insurance
- Maintenance
- Repair
- Spare Parts
- Office Supplies
- Other

This module does **not** represent an actual expense or financial transaction.

Actual expenses will be handled later by the Expenses module.

The sole responsibility of this module is to define and manage the available expense classifications and the minimal business rules associated with them.

---

## 2. Database Table

The module is based on the following existing table:

```sql
CREATE TABLE expense_types (
    id BIGSERIAL PRIMARY KEY,

    code VARCHAR(50) NOT NULL,
    name VARCHAR(100) NOT NULL,
    description VARCHAR(255),

    requires_pochi BOOLEAN NOT NULL DEFAULT TRUE,
    active BOOLEAN NOT NULL DEFAULT TRUE,

    created_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP,
    updated_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP,

    CONSTRAINT uk_expense_types_code UNIQUE (code),
    CONSTRAINT uk_expense_types_name UNIQUE (name)
);
```

The implementation must match the existing database structure.

Do not create, replace, or modify the database table as part of this module implementation.

## 4. Field Responsibilities

### 4.1 `id`

Database-generated primary key.

Rules:

- Generated by PostgreSQL through `BIGSERIAL`.
- The client must not provide it when creating an Expense Type.
- It must not be changed during an update.

---

### 4.2 `code`

Stable system identifier for the Expense Type.

Examples:

```text
INSURANCE
MAINTENANCE
REPAIR
SPARE_PARTS
OFFICE_SUPPLIES
OTHER
```

Rules:

- Required.
- Must not be blank.
- Maximum 50 characters.
- Must be unique.
- It is intended to remain stable and may be used by application logic.
- It is not the user-facing label.
- Normalize it consistently with the conventions already used by the project. If no convention exists, trim surrounding whitespace and convert it to uppercase before persistence.

Example:

```text
code = INSURANCE
name = Seguro
```

The `code` identifies the concept internally, while `name` is the human-readable value.

---

### 4.3 `name`

Human-readable name of the Expense Type.

Examples:

```text
Seguro
Mantenimiento
Reparación
Refacciones
Papelería
Otros
```

Rules:

- Required.
- Must not be blank.
- Maximum 100 characters.
- Must be unique.
- This is the value normally displayed to users in the frontend.
- Trim surrounding whitespace before persistence if that behavior is already used in the project.

---

### 4.4 `description`

Optional description providing additional information about the Expense Type.

Example:

```text
Mantenimiento preventivo y servicios periódicos del Pochi.
```

Rules:

- Optional.
- Maximum 255 characters.
- A blank description may be normalized to `null` if that matches existing project conventions.

---

### 4.5 `requiresPochi`

Indicates whether an Expense registered using this Expense Type must be associated with a specific Pochi.

Examples:

```text
INSURANCE
requiresPochi = true

MAINTENANCE
requiresPochi = true

REPAIR
requiresPochi = true

OFFICE_SUPPLIES
requiresPochi = false
```

Rules:

- Required in the domain model.
- Defaults to `true` when creating a record if the API design allows the field to be omitted.
- It does not create a relationship between Expense Type and Pochi.
- Expense Types must not contain `pochiId`.

Important:

This module does not validate the existence of a Pochi because Expense Types do not reference a specific Pochi.

The `requiresPochi` value will be consumed later by the Expenses module:

```text
requiresPochi = true
```

will mean that an Expense must have a Pochi association.

```text
requiresPochi = false
```

will allow an Expense without a Pochi association.

Do not implement that Expense validation yet.

---

### 4.6 `active`

Indicates whether the Expense Type is available for new Expenses.

Rules:

- Required in the entity.
- Defaults to `true` when creating a record.
- Inactive Expense Types must remain available for historical references.
- An inactive Expense Type must not be considered available for new operational Expenses.
- The future Expenses module will enforce whether inactive types may be selected during Expense creation.

---

### 4.7 `createdAt`

Represents when the Expense Type was created.

Rules:

- Generated automatically.
- Must not be supplied or modified by API clients.
- Follow the timestamp management pattern already used by AdministraPochi.

---

### 4.8 `updatedAt`

Represents the most recent modification of the Expense Type.

Rules:

- Managed automatically.
- Must not be supplied directly by API clients.
- Must be updated whenever the record is modified, following the existing project pattern.

## 5. Business Rules

### BR-01: Unique Code

Two Expense Types must not use the same `code`.

Invalid example:

```text
INSURANCE -> Seguro
INSURANCE -> Póliza
```

The service must validate uniqueness before persistence and return the project's established business/conflict error instead of relying exclusively on the database constraint.

The uniqueness validation must also account for normalized values if the code is normalized before persistence.

---

### BR-02: Unique Name

Two Expense Types must not use the same `name`.

Invalid example:

```text
REPAIR -> Reparación
POCHI_REPAIR -> Reparación
```

The service must validate uniqueness before persistence and return the project's established business/conflict error instead of relying exclusively on the database constraint.

Follow the same case-sensitivity behavior used by comparable catalog modules in the project. Do not introduce inconsistent duplicate rules only for this module.

---

### BR-03: Update Uniqueness Excludes the Current Record

When updating an Expense Type, uniqueness validations for `code` and `name` must exclude the current record.

Example:

Updating Expense Type `5` without changing its existing code and name must not generate a duplicate error against itself.

However, changing its code or name to values used by another record must be rejected.

---

### BR-04: Expense Type Is Not an Expense

An Expense Type must never contain transaction information.

The following concepts do not belong to this module:

- Amount.
- Expense date.
- Specific Pochi.
- Owner.
- Driver.
- Vendor or payee.
- Invoice number.
- Receipt or document.
- Payment information.
- Settlement.
- PochiAssignment.
- Administration Charge.
- User who recorded an actual Expense.

Those concepts belong to Expenses or other existing modules.

---

### BR-05: No Monetary Rules

Expense Types must not contain:

- Default amount.
- Expected amount.
- Calculation formulas.
- Settlement amounts.
- Administration fees.

Expense Types are classifications, not financial rule engines.

For example, `INSURANCE` must not define the monetary value of an insurance policy. Different insurance Expenses may have different amounts.

---

### BR-06: No Recurrence Rules

Do not add:

- Frequency.
- Recurrence.
- Next payment date.
- Renewal date.
- Effective periods.

Insurance policies may occur approximately every six months, but that frequency does not belong to Expense Types.

If future requirements introduce policy expirations, reminders, or renewals, those concepts must be modeled separately.

---

### BR-07: Historical Preservation

Expense Types may be referenced by Expenses.

For that reason, the application must favor deactivation over physical deletion.

Setting:

```text
active = false
```

preserves the Expense Type for historical records while preventing future operational use.

Do not introduce a separate `deleted` field or a generic soft-delete framework.

---

### BR-08: No Direct Pochi Relationship

`requiresPochi` is only a behavioral flag.

The Expense Type entity must not contain:

- `pochiId`
- `Pochi pochi`
- a collection of Pochis
- a Pochi repository dependency

The concrete Pochi association belongs to a future Expense record.

## 7. Create Expense Type

The API must allow creating an Expense Type.

Example request:

```json
{
  "code": "MAINTENANCE",
  "name": "Mantenimiento",
  "description": "Mantenimiento preventivo y servicios del Pochi",
  "requiresPochi": true
}
```

The client must not be required or allowed to control:

- `id`
- `createdAt`
- `updatedAt`

Creation behavior:

1. Validate the request DTO.
2. Normalize supported string values according to project conventions.
3. Validate unique `code`.
4. Validate unique `name`.
5. Assign defaults where applicable.
6. Map the request to the entity through MapStruct.
7. Persist the entity.
8. Return the response DTO.

Unless an established API pattern says otherwise, new Expense Types should be created with:

```text
active = true
```

Do not let a create request override system-managed timestamps.

## 9. Delete and Deactivation Behavior

Do not physically delete Expense Types through the normal API removal operation.

If a `DELETE` endpoint is implemented, it must logically deactivate the record:

```text
active = false
```

Expected behavior:

1. Find the Expense Type by ID.
2. Return the established not-found error if it does not exist.
3. Set `active` to `false`.
4. Update `updatedAt` according to project conventions.
5. Save the record.
6. Return the response/status used by comparable modules.

The record must remain in `expense_types`.

Do not call `repository.delete`, `deleteById`, or equivalent physical deletion methods from the normal service operation.

If the project already uses a specifically named `deactivate` operation rather than `DELETE`, follow that established convention.
